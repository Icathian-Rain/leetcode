# 第 1 天题解点评 - 数组与哈希

## 基本信息

- 日期：2026-04-24
- 主题：数组与哈希
- 覆盖题目：`217. Contains Duplicate`、`242. Valid Anagram`、`49. Group Anagrams`
- 本次结果：三题均完成，语法验证通过

## 用户思路概述

`217. Contains Duplicate` 使用 `unordered_set` 维护已经出现过的数字，遍历时一旦发现当前数字已在集合中，就立即返回 `true`。

`242. Valid Anagram` 使用长度为 26 的计数数组，先统计 `s` 中字符出现次数，再用 `t` 抵消，最后检查所有计数是否归零。

`49. Group Anagrams` 为每个字符串复制一份并排序，把排序后的字符串作为哈希表 key，将同组字符串收集到同一个 `vector<string>` 中。

## 评价

- 题意理解：很好 - 三题都抓住了“相同状态归并 / 判重 / 频次抵消”的核心。
- 思路质量：较好 - `217` 和 `242` 都是本主题下非常直接的表示方式；`49` 使用排序 key 也很稳，是标准可通过方案。
- 正确性：很好 - 在 LeetCode 默认约束下，三份代码逻辑正确，且已通过 `g++ -std=c++20 -fsyntax-only` 验证。
- 复杂度意识：较好 - `217` 是期望 `O(n)`，`242` 是 `O(n)`；`49` 当前是 `O(n * k log k)`，其中 `k` 是单词长度。
- 边界覆盖：较好 - 空字符串、单字符、重复元素这些基础边界都能自然处理。
- 代码清晰度：较好 - 实现短而清楚，变量数量克制，没有把简单题写复杂。
- 当前最重要的成长点：开始主动比较“排序签名”和“计数签名”这两种 key 的取舍。

## 做得好的地方

- `217` 的早返回写得很自然，说明你已经能把“是否存在重复”转成“遍历过程中是否见过”的动态判断。
- `242` 的频次抵消写法简洁，后续很多字符串计数题都能复用这个骨架。
- `49` 能主动把异位词转成统一签名，再用哈希表分组，说明你已经从“判断两个字符串是否同类”过渡到了“批量归类”。

## 需要改进的地方

- `242` 可以先判断 `s.size() != t.size()` 并提前返回，虽然当前计数检查也能得出正确结果，但提前判断能让意图更清楚。
- `49` 当前使用排序签名是正确方案，但它没有完全延续 `242` 的 26 位计数思路。作为本周训练，可以再写一版计数签名，强化“频次状态也能做 key”的模式。
- `49` 中 `for (auto str: strs)` 会复制字符串，`for (const auto& str : strs)` 更适合这里；遍历哈希表时也可以使用引用，减少不必要拷贝。
